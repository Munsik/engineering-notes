> Don't document the feature. Document the engineering decisions behind using it in production.

공식 문서는 기능이 무엇이고 어떻게 설정하는지를 알려 줍니다.
여기서는 그다음 이야기를 합니다. 그 기능을 실제 서비스에 올릴 때 무엇을 정해야 하고, 왜 그렇게 정하는지입니다.

## 글의 기본 단위는 use case

글을 제품 기능별로 나누지 않고, 풀어야 할 문제 하나를 정해서 그 과정에서 생기는 결정을 순서대로 따라갑니다.
그래서 글마다 대체로 이런 질문에 답하려고 합니다.

1. 왜 이 기술이 필요한가
2. 어떤 조건에서 효과가 있고, 어떤 조건에서는 맞지 않는가
3. 설계할 때 무엇을 결정해야 하는가
4. 실제로 어떻게 구현하는가
5. 프로덕션에서 무엇이 잘못될 수 있는가
6. 어떻게 검증하고 운영하는가

## 글의 세 가지 유형

| 유형 | 목적 | 예시 |
| --- | --- | --- |
| Deep Dive | 하나의 설계 결정을 실험과 함께 깊게 분석 | Bucket span을 정하는 기준 |
| Practical Guide | 적용 절차를 재현 가능한 설정과 함께 정리 | Anomaly detection job 프로덕션 배포 |
| Engineering Perspective | 현장 경험에서 나온 판단 기준 | High cardinality가 ML 사이징 가정을 깨는 이유 |

## 쓸 때 지키는 것

"데이터에 따라 다르다"로 끝내지 않으려고 합니다. 어떤 조건에서 어떤 결과가 나왔는지를 설정과 함께 보여 주는 게 목표입니다.
실험에 쓴 synthetic data 생성 코드와 설정은 저장소의 `labs/` 폴더에 같이 둡니다. 읽는 분이 직접 돌려 볼 수 있어야 하니까요.

글마다 기준 버전을 적고, GA가 아닌 기능은 tech preview 같은 상태를 같이 적습니다.
현장 경험은 업종 수준으로만 이야기하고, 특정 환경을 알아볼 수 있는 정보는 넣지 않습니다.

틀린 내용을 발견하시면 GitHub issue로 알려 주세요. 고친 이력은 저장소에 그대로 남습니다.
