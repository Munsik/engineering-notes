# 용어와 문체 기준

Engineering Notes의 모든 글에 적용하는 기준입니다. 읽는 사람은 Elastic을 쓰는 한국 엔지니어와 고객입니다. 그 사람들이 회의와 문서에서 실제로 쓰는 말을 씁니다. 영어 표현을 한국어로 옮긴 듯한 문장과, AI가 흔히 만드는 문장 틀은 쓰지 않습니다.

`engineering-notes-writing` 스킬의 문체 절과 함께 봅니다. 둘이 어긋나면 이 문서를 따르고 스킬을 고칩니다.

## 1. 영어 그대로 두는 말

한국 엔지니어가 평소 영어로 말하는 기술 용어는 번역하지 않습니다. 억지로 옮기면 오히려 무슨 말인지 모르게 됩니다.

| 영어 그대로 | 쓰지 않는 번역 |
| --- | --- |
| Search, Observability, Security (Elastic 솔루션 이름) | 검색, 관측성, 보안 탐지 시스템 |
| SIEM, APM, SLO | 보안 정보 이벤트 관리 등 |
| shard, replica, primary, segment, mapping, index template, data stream, rollover | 조각, 사본, 원본 shard, 매핑 구조 |
| source of truth | 기준 원본, 진실의 원천 |
| breaking change | 깨지는 변경 |
| rolling restart, rolling upgrade | 순차 재시작(문맥상 필요할 때만 "순차 업그레이드") |
| JVM heap, off-heap, GC, circuit breaker | 힙 밖, 회로 차단기 |
| drift, runbook, postmortem 대신 쓰는 "사후 분석"은 허용 | 표류 |
| failure store, DLQ, persistent queue(PQ) | 실패 저장소, 영구 큐 |
| anomaly score, bucket span, influencer, datafeed | 이상 점수 구간 등 |

같은 용어를 한 글 안에서 영어와 한국어로 섞어 쓰지 않습니다.

## 2. 한국어로 쓰는 말

한국 IT 현장에서 이미 굳어진 한국어가 있으면 그 말을 씁니다.

| 쓰는 말 | 쓰지 않는 말 | 비고 |
| --- | --- | --- |
| 변경 관리 | 변화 관리 | 변화 관리는 조직 변화 관리(change management) 뜻으로 읽힘 |
| 데이터 소스, 로그 소스, 소스 | 원천 | "원천 데이터" 같은 굳은 표현만 예외 |
| 로그, 메트릭, 트레이스 | 로그와 지표 데이터 | 모니터링 수치를 말할 때 "CPU 사용률 지표"처럼 "지표"는 씀 |
| 생명주기 | 생애 | |
| 무거운 query | 비싼 query | |
| 성능 저하, 병목 | 느려짐, 어디서 막혔는지 | |
| 이상 징후 | 이상 신호 | |
| replica(shard 맥락), 복사본(일반) | 사본 | |
| 구조, 형태 | 모양 | "데이터를 어떤 모양으로 둘지" 같은 표현 |
| 조회하다 | 꺼내 보다 | |
| 확인하다, 검증하다 | 증명하다 | 감사처럼 실제로 증빙을 내야 할 때만 "증빙" |
| 수집하다 | 들여오다 | |
| 롤백, 되돌리기 | | 둘 다 씀. 한 글 안에서는 하나로 맞춤 |
| 계층 | 층 | "네 층" 대신 "네 계층"이나 대상을 직접 나열 |
| 유지되다 | 살아남다 | |
| 자주 묻는 질문 | 자주 받는 질문 | |

## 3. 비유와 직역 표현

영어에서 자연스러운 비유를 그대로 옮기지 않습니다.

| 쓰지 않는 표현 | 바꾼 예 |
| --- | --- |
| 바뀌는 것의 지도, 컬렉션 지도 | 변경 대상 정리, 컬렉션 구성 |
| 변경을 흘려보내는 절차 | 변경 절차 |
| 위에 얹는다 | `@custom`으로 덮어쓴다, 추가한다 |
| 다리 역할 | 연결, 중간 단계 |
| 길을 잃다, 큰 그림 | 전체 구성 |
| 손을 대다(과용) | 고치다, 바꾸다 |

## 4. 문장 틀

AI가 쓴 글에서 반복되는 틀입니다. 쓰지 않습니다.

- 예고 문장: "이 글은 ~를 정리합니다", "이번 장에서는 ~을 살펴봅니다", "그렇다면 ~는 무엇일까요?". 글 첫머리는 문제와 조건으로 바로 시작합니다. 글의 범위를 꼭 밝혀야 하면 "~은 다음 글에서 다룹니다"처럼 범위 밖만 짧게 적습니다.
- 빈 강조어: "핵심은", "결론적으로", "즉,", "다양한", "효과적으로", "강력한", "원활한", "중요한 역할을 합니다".
- "~하는 것입니다", "~라는 뜻입니다"를 문장마다 붙이는 것. 대부분 "~합니다"로 줄일 수 있습니다.
- "~할 수 있습니다"가 연속으로 나오는 것.
- 문단 끝 요약 한 줄, 굵은 글씨 남발, 이모지, em dash(—).
- 소개 문구를 영어 마케팅 문장처럼 쓰는 것. 예: "검색, 로그와 지표 분석, 보안 탐지 시스템을 프로덕션에서 설계하고 운영하는 문제를 다룹니다" 대신 "Elastic Stack으로 Search, Observability, Security 환경을 구축하고 운영할 때 필요한 설계와 운영 기준을 정리합니다".

## 5. 제목

- 글 제목은 질문형이어도 됩니다. 다만 한국 엔지니어가 실제로 할 법한 질문으로 씁니다. 예: "클러스터가 느려질 때 병목을 어떻게 찾는가".
- sidebar label은 명사형으로 짧게 씁니다. 예: "05. 성능 저하".
- 절 제목은 질문형을 쓰지 않습니다.
- 제목을 바꾸면 anchor가 바뀌므로 그 절로 오는 링크를 같이 고칩니다.
